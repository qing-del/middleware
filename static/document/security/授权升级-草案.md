# 授权升级\-草案

# 背景

- 为了让 CORE NODE 与新的 CORE AGENT 适配，需要给 CORE AGENT 加入授权服务器的端点

- 故所以需要在 CORE NODE 中加入一个授权服务器，采取基于 OAuth2 基础上做自定义的授权方式

- 为了能够定义 CORE AGENT 中可以获取到读取 CORE NODE 中的信息



# 架构设计

## 框架规定与构思

- 新的授权框架不采用自主手搓的方式，采取 Spring Security 的现有框架搭建新的授权登录体系

    - 需要设计 RABC 框架，采用新的表设计

    - 采取公钥、私钥签名方式来签发token，开放接口白名单获取公钥`pub`（JWT algorithm: RS256）

    - 当前项目使用 Spring Boot 4.0.5，安全相关依赖跟随其 BOM 管理的 Spring Security 7.0.4，不在项目中显式覆盖 Spring Security 版本。

- CORE AGENT 的获取信息的接口来自 CORE NODE 的`middleware-open-api-agent`模块

- 第一版的权限设置先按照admin和user身份，采取`module:oper`这种方式来定义

    - `oper`先暂定`read`、`write`、`manage`、`super`（四者相互独立，没有联系）

        - `manage`是专门给管理员使用的

        - `super`是一些`creator`专属的接口才开放的

- 本期固定 registered client 仅为 `user`、`admin`、`core_agent`：前两者是第一方 internal client，后者是 PKCE public client；所有 access token 统一采用 RS256，并通过`client_id`和`grant_type`决定授权方式。



## CORE AGENT 授权方式

- `core_agent` 是 public client：以 PKCE S256 为核心安全保证，不依赖 `client_secret`。

- 当前暂定回调地址为`http://127.0.0.1:9090/oauth/callback`；后续通过客户端配置调整，启用授权码流程时必须存在有效的已注册回调地址。

- `core_agent`的首次授权通过 OAuth Authorization Endpoint 发起，参数必须包括`response_type=code`、`client_id=core_agent`、精确匹配的`redirect_uri`、`state`、可选`scope`、`code_challenge`和`code_challenge_method=S256`。

- Authorization Endpoint 必须严格校验 active client、精确 redirect URI、唯一 S256 方法和账号默认/extra grant；具体 endpoint path 由 Authorization Server 设置确定，本草案不自行命名路径。

- 首版 Authorization Endpoint 使用 Spring Authorization Server 默认的`/oauth2/authorize`；Token Endpoint 固定为`POST /oauth/token`。这两个协议端点之外，服务端提供仅供该浏览器授权流程使用的 Thymeleaf 页面：`GET/POST /oauth/login`完成用户名/密码登录，`GET /oauth/consent`展示授权确认；consent 表单提交回标准 Authorization Endpoint。它们不是 USER/ADMIN internal JSON API，不改造 frontend/。
- Spring Authorization Server 7.0.4 保留标准`OAuth2AuthorizationEndpointFilter`、其默认 GET/POST converter 与标准 redirect 响应形状；但在`authorizationEndpoint.authenticationProviders(...)`中移除默认的授权请求与 consent provider，替换为 CORE AGENT 项目 provider。项目 provider 使用既有 PKCE、consent、Redis auth-code application service；不得写入 SAS `OAuth2Authorization`或 SAS authorization code，避免与`CoreAgentAuthorizationCodeStore`形成双真相。
- 浏览器仅在等待 consent 的期间将授权请求 transaction 存入 HttpSession，TTL 与浏览器 session 同为 10 分钟；其中只保存完成标准 endpoint 校验所需的绑定数据和已认证主体，不保存 raw auth code、access token、refresh token。最终 raw auth code 只在用户确认后写入`CoreAgentAuthorizationCodeStore`。
- 自定义 consent 页面提交回`POST /oauth2/authorize`，保留标准`client_id`、`state`和重复`scope`参数，并额外提交`consent_action=approve|deny`和 CSRF token。wrapper converter/details 将该 action 交给项目 consent provider：`approve`由服务端重算范围并强制加入 auto_approve（即使 optional scope 为空）；`deny`一律按标准 redirect 返回`access_denied`，不信任 hidden mandatory 字段，也不保存 consent 或签发 code。

- CORE AGENT 浏览器授权首版仅支持`username/password`。`email-code`继续只属于`user`、`admin` internal client 的`/oauth/email-code`与`/auth/login`流程；不得借此扩大其 endpoint 的 client 范围。

- Authorization Server 浏览器 session 的有效期为 10 分钟，Cookie 必须为`HttpOnly`、`SameSite=Lax`，生产环境必须为`Secure`。Spring Authorization Server 7.0.4 会对其全部 endpoint matcher 添加 CSRF ignore，不能用普通 DSL 取消；因此额外注册精确 browser CSRF filter，且只保护`POST /oauth/login`与`POST /oauth2/authorize`。`POST /oauth/token`和 Bearer `POST /oauth/logout`不匹配该额外 filter，按精确路径豁免；不得使用宽泛 OAuth 路径忽略。所有来源地址均只读取 socket remote address，不信任`X-Forwarded-For`。

1. CORE AGENT 本地生成`code_verifier`与对应的 S256 `code_challenge`，再跳转至 OAuth Authorization Endpoint。

2. 用户完成登录并确认 consent；effective scope 为 client scopes ∩ rank-role permissions ∩ 用户本次 consent，写入`oauth2_authorization_consent`。请求未带`scope`时，以 core_agent 的`auto_approve`作为 consent 页面候选；其中 auto_approve 是强制项，用户不能取消，只能勾选额外可选权限。已保存 consent 可用于相同范围的后续授权，新增范围仍须重新确认。

3. 服务端生成一次性 256-bit `auth_code`，在 Cache 保存 10 分钟，并以已注册 redirect URI 回调，携带标准`code`和原始`state`。

4. CORE AGENT 向`POST /oauth/token`提交`grant_type=authorization_code`、`client_id=core_agent`、`code`、`redirect_uri`和`code_verifier`。成功兑换立即原子删除 code，并返回 RS256 `access_token`与 rotating `refresh_token`。

5. CORE AGENT 通过`POST /oauth/token`的`refresh_token`技术 grant 续期；通过`POST /oauth/logout`注销当前 client + user session。

> IP 在授权时记录 socket remote address；兑换时 IP 不同只记录安全告警，不拒绝兑换。

> `jacolp.oauth2.rs256.enabled=false`保留既有签名/校验链，Phase 2-4 的 RS256 Authorization Server 与 internal endpoint 不接线；设为`true`后，新授权相关 token 一律使用 RS256 非对称签名与校验。Phase 5 才把 Resource Server 对全部业务请求的认证完全切换到该体系。



## 授权架构

- 令牌有效期

    - USER和ADMIN授权都是访问令牌有效3h，然后刷新令牌有效3天

    - CORE AGENT授权的访问令牌有效 1 小时，刷新令牌有效 24 小时；是否续期与 rotation 均由其`token_settings`控制，首发配置强制 rotation。

- 刷新机制

    - 当访问令牌过期，刷新令牌还有效的时候

        - 自动重新生成访问令牌

        - 然后生成一个新的刷新令牌，废除原有的刷新令牌

    - 如果刷新令牌过期则需要重新授权

- 令牌存储方式

    - 采用混合方式存储

        - 黑名单：如果使用`access_token`能在`Cache`中获取到对应的信息则说明令牌已注销

        - 白名单：如果在`Cache`中能够用`refresh_token`查询出对应认证的信息，说明刷新令牌有效

> 还会根据后续情况来确定是否需要调整
> 
> 



# 架构规定

- 关于`sys_user.username`字段，后续只允许`creator`去修改

- RSA Key的生成方式使用 openssl 获取

```Bash
# 私钥的生成指令
openssl genpkey -algorithm RSA -out key -pkeyopt rsa_keygen_bits:2048
# 基于私钥生成公钥指令
openssl pkey -in key -pubout -out key.pub
```

- RSA 密钥对的存储位置（对应模块的相对资源路径）（不得提交git）

    - 私钥：`/resource/key/key`

    - 公钥：`/resource/key/key.pub`

- 加密存储采用**单向哈希加密\(bcrypt\)**

- `jti`的生成采取**128 bit 随机数 \+ Base64 URL Safe**

- `authorization_code`和`refresh_token`本体采用`256 bit 随机数`

- USER / ADMIN 登录授权：client scopes ∩ 账号角色（按 rank 继承）权限 ∩ 请求 scopes；未请求 scope 时以 auto\_approve 作为第三个交集。交集采用下文的模式求交，不是精确字符串相等，也不展开为完整权限目录。

- CORE AGENT 授权：client scopes ∩ 账号角色（按 rank 继承）权限 ∩ consent scopes。

- token中携带的信息（首发`aud`统一为`core-node-api`）

```JSON
{
  "iss": "core-node",
  "sub": "12345",
  "aud": ["core-node-api"],
  "iat": 1720000000,
  "exp": 1720010800,
  "jti": "...",
  "client_id": "core_agent",
  "grant_type": "authorization_code",
  "username": "jacolp",
  "roles": ["admin"],
  "scope": [
    "note:read",
    "sys:read"
  ]
}
```

- `*`是通用符号：`*:read`可以匹配`note:read`，也可以匹配`media:read`。第一版 DB 与 JWT `scope` 均保留通配符，不在签发时展开；由统一鉴权 Util 进行匹配。

### Scope 模式求交

- 首版 scope 是严格的 `resource:action` 双分量模式，恰有一个冒号；每个分量是合法 token 或单独的 `*`。模式大小写敏感，签发前必须 trim 并拒绝空值、格式错误或同一输入集内的重复值。

- 三方交集对每一对模式逐分量计算：相同分量保留；一方为`*`时取另一方；两个不同的具体分量没有交集。不会查询或枚举 permission catalogue。

- 因此，角色`*:read` ∩ client `note:read` ∩ request `note:read`的 JWT scope 是`note:read`；反向顺序同样取更具体的模式。双方都是`*`时才保留`*`，例如`*:read` ∩ `*:read` = `*:read`。

- 请求携带 scope 时，计算角色 ∩ client ∩ request；未携带（`null`）时计算角色 ∩ client ∩ auto\_approve。显式空 scope 集是明确请求空权限，不等同于未携带。

- 任意 `*:super` 或 `resource:super`结果，只有角色代码精确为`CREATOR`、client 允许，且本次明确请求 scope 中存在可与它求交的`super`模式时才可保留。`auto_approve`永不自动签发`super`；普通 admin 即使 client 配置了`*:super`也不会获得它。

# 实体设计

## MySQL实体模型

### sys\_user

- `extra_grant_types`只保存账号显式附加的授权方式，首发默认空字符串；本期不再将默认授权方式写入账号行。

- 配置默认账号授权方式固定为`password,email-code,authorization_code`：正常账号默认拥有它们；其中`authorization_code`仍须由客户端显式允许。

## Cache存储内容

- 令牌缓存模式：

    - user:blacklist:access:\{jti\}

    - user:session:\{client\_id\}:\{user\_id\}

        - current access `jti`、access expiry、current refresh fingerprint、refresh expiry

    - auth\_code:\{auth\_code\}

        - `client_id=core_agent`

        - exact `redirect_uri`

        - consent scopes

        - `code_challenge`与`code_challenge_method=S256`

        - original socket remote address

        - `user_id,username,role_id,password,email,extra_grant_types,status`安全字段快照；密码仅为已存储的密码哈希，严禁日志、响应或`toString`暴露。

    - user:auth\_code:\{user\_id\} \-\> auth\_code

        - 原子指针；同一用户新 code 生成时替换旧 code 并使旧 code 失效。

        - 用户安全字段`status,role_id,password,email,username,extra_grant_types`变更时，立即使该用户当前 auth code 失效。

# 授权接口



## USER / ADMIN Internal Login

- 路径：`POST /auth/login`。它只服务`user`、`admin`两个 internal client，与 CORE AGENT 的 OAuth Authorization Endpoint 分离。

- 所有请求均以`(client_id,grant_type)`选择授权规则；internal client 不传`client_secret`。

- `client_id=user|admin`，允许的`grant_type`均为`password`、`email-code`。客户端、账号默认/extra grant、账号状态、socket remote address 的`allowed_ips`均须校验。

- `grant_type=password`携带`username`、`password`；`grant_type=email-code`携带`email`、`code`。

- `scope`可选。传入`scope`时，最终权限为账号角色（按`rank`继承）权限 ∩ client scopes ∩ 请求 scopes；未传时为账号角色权限 ∩ client scopes ∩ auto\_approve。具体采用“Scope 模式求交”，不要求三个字符串完全相同，也不将 wildcard 展开。

- `*:super`只能在 creator 角色、client 允许、且本次明确请求三者同时满足时签发；不会因普通 admin 登录而默认签发。

- 成功响应签发 RS256 `access_token`与按 client `token_settings`控制的 refresh token；refresh 仅通过 client 的`refresh_token`技术 grant 续期。

- 目标架构删除旧`/user/user/login`、`/admin/user/login`，不保留 compatibility adapter。

## 登录邮箱验证码

- 路径：`POST /oauth/email-code`，参数为`client_id,email`；仅接受`user`、`admin` internal client，响应不得泄漏账号或邮箱是否存在。

- 验证码独立于激活和换邮箱验证码：6 位数字、TTL 10 分钟；同一`(client_id,user)`同一时刻仅一条有效记录。

- 每邮箱、每 IP 均执行 60 秒冷却和每小时 5 次发送限制；兑换失败满 5 次立即失效。

- Redis 只保存 BCrypt verifier 与`client_id,user_id,email`绑定信息；成功兑换必须原子消费，不能复用 activation 或 email-change 的 key、payload、发送/消费逻辑。
- 登录验证码是一次性凭据，渲染后的验证码邮件不得进入`sys_event_outbox`或`EmailSendRequestedEvent`；必须使用独立的同步 SMTP 投递路径。
- 同步 SMTP 投递失败时，签发服务必须 fail-closed：立即清理对应`(client_id,user_id)`的登录验证码 Redis state；已占用的邮箱/IP 限流记录保留，不因投递失败回滚。
- 登录验证码不得复用 activation 或 email-change 的服务、邮件模板或 Redis key；现有 activation 流程及其协议保持不变。

## USER / ADMIN Internal Logout

- 路径：`POST /auth/logout`，仅接受经验证的 user/admin RS256 Bearer access token。

- 注销当前`client_id + user_id`会话：将当前 access token 的`jti`写入 blacklist，删除当前 refresh token 与 session；不影响其他 client 的会话。

- 目标架构删除旧`/user/user/logout`、`/admin/user/logout`，不保留 compatibility adapter。


# 后续管理能力

- 本期固定注册客户端目录严格为`user`、`admin`、`core_agent`；不得创建第四个客户端或恢复`authorization_client`。仅`creator`可管理已注册 OAuth client 的后续能力，必须在单独阶段设计和实施。

- 管理 endpoint/DTO、未来客户端的认证方式与生命周期、审计与启停安全规则不属于当前 Phase 1-7 的实现与验收范围，除非后续另行启动该阶段。
