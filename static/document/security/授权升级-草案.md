# 授权升级\-草案

# 背景

- 为了让 CORE NODE 与新的 CORE AGENT 适配，需要给 CORE AGENT 加入授权服务器的端点

- 故所以需要在 CORE NODE 中加入一个授权服务器，采取基于 OAuth2 基础上做自定义的授权方式

- 为了能够定义 CORE AGENT 中可以获取到读取 CORE NODE 中的信息



# 架构设计

## 框架规定与构思

- 新的授权框架不采用自主手搓的方式，采取 Spring Security 的现有框架搭建新的授权登录体系

    - 需要设计 RABC 框架，采用新的表设计

    - 采取公钥、私钥签名方式来签发token，开放接口白名单获取公钥`pub`（JWT algorithm: RS256）

    - 当前项目使用 Spring Boot 4.0.5，安全相关依赖跟随其 BOM 管理的 Spring Security 7.0.4，不在项目中显式覆盖 Spring Security 版本。

- CORE AGENT 的获取信息的接口来自 CORE NODE 的`middleware-open-api-agent`模块

- 第一版的权限设置先按照admin和user身份，采取`module:oper`这种方式来定义

    - `oper`先暂定`read`、`write`、`manage`、`super`（四者相互独立，没有联系）

        - `manage`是专门给管理员使用的

        - `super`是一些`creator`专属的接口才开放的

- 这个版本收敛一件事情，将管理员登录、用户登录、第三方登录采用同一套的签名方式，通过`client_id`来判定授权的方式



## CORE AGNET 登录方式

- `core_agent` 是 public client：以 PKCE S256 为核心安全保证，不依赖 `client_secret`。

- 当前暂定回调地址为`http://127.0.0.1:9090/oauth/callback`；后续通过客户端配置调整，启用授权码流程时必须存在有效的已注册回调地址。

- CORE AGENT 的 `agent_client` 与后续 `authorization_code` 兑换均绑定同一个 `core_agent` registered client。

1. 点击使用 CORE NODE 授权

    1. 生成 `code_verifier`

    2. 使用对应的加密方式得到 `code_challenge`

2. 携带对应信息跳转到 CORE NODE 的授权页面（`grant_type`=`agent_client`）

    1. 登录成功

    2. 询问用户所颁发的 `scopes`，后存储到`oauth2_authorization_consent`中

    3. 生成一个一次性`auth_code`（单纯一个字符串）

    4. 存储到Cache中，`auth_code` \-\> `Map`，10 分钟 TTL，成功兑换后立即删除

    5. 用回调地址传递`auth_code`

3. 确认授权之后 CORE NODE 回调对应的地址

4. CORE AGENT 拿到对应的`auth_code`之后，使用`code_verifier`进行授权登录（`grant_type`=`authorization_code`，仅支持 PKCE S256）



> 补充：
> 
> - `auth_code` \-\> `ip`是为了安全问题，所以后续采用`authorization_code`的授权方式时，需要重新校验一次请求头中的`ip`
> 
> - `auth_code`的作用是缓存用户信息，后续采取`authorization_code`登录时，才会真正走一次权限交集运算做权限和信息补全
> 
> 



## 授权架构

- 令牌有效期

    - USER和ADMIN授权都是访问令牌有效3h，然后刷新令牌有效3天

    - AGENT授权是访问令牌有效1h，首版不签发刷新令牌

- 刷新机制

    - 当访问令牌过期，刷新令牌还有效的时候

        - 自动重新生成访问令牌

        - 然后生成一个新的刷新令牌，废除原有的刷新令牌

    - 如果刷新令牌过期则需要重新授权

- 令牌存储方式

    - 采用混合方式存储

        - 黑名单：如果使用`access_token`能在`Cache`中获取到对应的信息则说明令牌已注销

        - 白名单：如果在`Cache`中能够用`refresh_token`查询出对应认证的信息，说明刷新令牌有效

> 还会根据后续情况来确定是否需要调整
> 
> 



# 架构规定

- 关于`sys_user.username`字段，后续只允许`creator`去修改

- RSA Key的生成方式使用 openssl 获取

```Bash
# 私钥的生成指令
openssl genpkey -algorithm RSA -out key -pkeyopt rsa_keygen_bits:2048
# 基于私钥生成公钥指令
openssl pkey -in key -pubout -out key.pub
```

- RSA 密钥对的存储位置（对应模块的相对资源路径）（不得提交git）

    - 私钥：`/resource/key/key`

    - 公钥：`/resource/key/key.pub`

- 加密存储采用**单向哈希加密\(bcrypt\)**

- `jti`的生成采取**128 bit 随机数 \+ Base64 URL Safe**

- `authorization_code`和`refresh_token`本体采用`256 bit 随机数`

- 用户登录授权：登录客户端权限 ∩ 账号角色权限

- 子系统CORE AGENT授权：登录客户端权限 ∩ 账号角色权限 ∩ 所颁发的权限

- token中携带的信息（首发`aud`统一为`core-node-api`）

```JSON
{
  "iss": "core-node",
  "sub": "12345",
  "aud": ["core-node-api"],
  "iat": 1720000000,
  "exp": 1720010800,
  "jti": "...",
  "client_id": "core_agent",
  "grant_type": "authorization_code",
  "username": "jacolp",
  "roles": ["admin"],
  "scope": [
    "note:read",
    "sys:read"
  ]
}
```

- `*`是通用符号：`*:read`可以匹配`note:read`，也可以匹配`media:read`。第一版 DB 与 JWT `scope` 均保留通配符，不在签发时展开；由统一鉴权 Util 进行匹配。

- `authorization_client`是通用第三方授权码客户端的预留名称；首版不参与 CORE AGENT 授权链。



# 实体设计

## MySQL实体模型

### sys\_user

- 新增`grant_types`字段控制账号可以使用的授权方式

    - USER：`password,user_password,agent_client`

    - ADMIN、CREATOR：`admin_password,agent_client`

    - `authorization_code`默认允许所有正常账号使用，但不写入该字段；客户端仍须显式允许对应的`grant_type`

    - `refresh_token`不是账号授权方式，不写入该字段；刷新能力由客户端授权方式和`token_settings`控制

### sys\_role

- 新增`rank`字段（不再通过原有实现的`id`大小控制角色的等级，越小等级越高）

    - 首版将 VIP 用户全部迁移为 USER 后删除 VIP 角色及其残留授权关系；CREATOR、ADMIN、USER 的等级由`rank`负责。

> 原作用于修改用户信息的权力范围
> 
> 

### oauth2\_registered\_client

> 基于原有的协议，做一点自定义字段
> 
> 

- client\_id

- cilent\_secret（密文存储；public client 可为空）

- client\_secret\_expires\_at

- authorization\_grant\_types（允许的授权方式）

- client\_authentication\_methods（首期默认client\_secret\_post）

- scopes（可以申请的权限）

- auto\_approve（默认自带的权限）

- redirect\_uris（回调地址）

- status（active,disabled）

- client\_id\_issued\_at

- client\_settings

- token\_settings（访问令牌有效期、refresh token 及 rotation 等 token 配置的唯一真相）

- allowed\_ips



### oauth2\_authorization\_consent

- registered\_client\_id

- principal\_name（采用sys\_user\.id）

- authorities



### sys\_permission

- code（note:read）

- oauth\_scope（node\.read）

- resource（note）

- action（read）

- status（active，disabled）

- description



### sys\_role\_perm

> 角色权限表，颁发token的时候根根据这个表来界定权限范围
> 
> 

- role\_id

- perm\_id

- grant\_time

# 授权接口



## 获取 Access Token

- 路径：`/oauth/token`

- 接口统一

    - 将用户登录、管理员登录、第三方登录都归纳到同一个接口上面

    - 使用`client_id`和`grant_type`去判定使用的登录方式

    - 通过DB查询出来对应客户端的授权准则

- 规范

    - Bearer类型的access\_token



### 非 authorization\_code 方式

#### `grant_type`=`password`or`admin_password`

- Map需要携带以下信息（账密形式）

    - Username

    - Password

- Map需要携带以下信息（邮箱形式）

    - Email

    - code

- 授权方式

    - 签发`access_token`和`refresh_token`

#### `grant_type`=`agent_client`or Other

- Map需要携带以下信息（账密形式）

    - Username

    - Password

- Map需要携带以下信息（邮箱形式）

    - Email

    - code

- 授权方式

    - 签发`auth_code`



### authorization\_code 方式

- Map需要携带以下信息（账密形式）

    - client\_id

    - client\_secret（仅需要客户端认证的 client 携带；`core_agent` 不携带）

    - auth\_code

    - code\_verifier

- 授权形式

    - `core_agent`签发`access_token`；其他允许 refresh 的客户端按其`token_settings`签发`access_token`和`refresh_token`



## 注销登录

- 路径：`/oauth/logout`

- 统一接口

    - 将用户登录、管理员登录、第三方登录都归纳到同一个接口上面

    - 使用`client_id`和`grant_type`去判定使用的授权方式

    - 按照黑名单方式将两个`token`写入Cache中

> 仅仅注销当前的`access_token`和对应的`refresh_token`
> 
>
